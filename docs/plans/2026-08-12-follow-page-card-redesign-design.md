# 跟单页策略卡改版设计（2026-08-12）

把 `/follow` 从「12 张平铺大卡 × 14 个指标」改成「克制的卡片 + 下沉的详情 + 可交互的大图」。

---

## 1. 背景：2 档时代的密度，到 12 档变成了反效果

策略档位从 2 扩到 12 之后（见 `2026-08-11-follow-strategy-tiers-design.md`），页面结构没有跟着变：

|                    | 数字                                               |
| ------------------ | -------------------------------------------------- |
| 每张策略卡的指标数 | **14 个**                                          |
| 策略数             | 12                                                 |
| 同屏数字总量       | **168 个**                                         |
| 卡片布局           | `auto-fit minmax(320px, 1fr)` → 桌面约 3 列 × 4 行 |
| 估算页面高度       | 3000px+（卡片区独占 1600–2000px）                  |

14 个指标在 2 档时代是合理的 —— 两张卡并排，可以逐项对照「保守 vs 激进」，每个指标都是主角。

到 12 档，同样的密度失效：**168 个数字里没有主次结构**。要回答最基本的「哪一档表现最好」，得在 4 行卡片之间横跳着比 12 个「结算净值」，而它们分散在不同族分组里、字号还都一样。

**另一个眼下就会发生的现实**：10 条新档刚种进去，战绩全是空的。现在的布局对「有数据」和「无数据」一视同仁 —— 12 张同样大小的卡，其中 10 张写满「—」。这不只是难看，它会让人误判成「新档都不工作」。

---

## 2. 用户裁决

| #   | 决策           | 选择                                                   |
| --- | -------------- | ------------------------------------------------------ |
| U1  | 页面主要用途   | **横向对比** —— 「哪一档表现最好」                     |
| U2  | 排序           | **不做排序，固定按信号族分组**（保持既有四族顺序）     |
| U3  | 呈现形式       | **卡片**（不是表格）；首页克制表达，更多信息放策略详情 |
| U4  | 大图去留       | **保留，加族筛选 + hover 高亮**                        |
| U5  | sparkline 缩放 | **各自缩放**（横比职责交给大图，卡上优先保证形状可读） |

参考视觉：量化平台的「策略超市」式卡片 —— 卡片主体是迷你净值曲线，配 4 个核心数字，细节收在「查看详情」后面。

---

## 3. 三层结构

### 3.1 卡片层（首页克制表达）

每卡保留 **1 条 sparkline + 4 个核心数字 + 3 个元信息 + 1 个详情入口**。

**留在卡上的 4 个**（回答「哪一档最好」直接相关）：结算净值 · ROI · 结算胜率 · 最大回撤
**元信息行**：已结算 N 仓 · 持有 M · 运行 X 天
**下沉的 10 个**：平均年化 / 累计追价成本 / 协议费 / 净盈亏(含成本) / 均延迟成本 / 均执行滑点 / 开始时间 / 运行时间 / 最大占用资金 / 建议跟单额度

**sparkline 各自缩放**（U5）：每卡按自己的 min/max 定域，不统一 Y 轴 —— 统一缩放会把小额档压成平线。卡上不画坐标轴，只画形状：240×52 的区域塞不下可读的刻度。横向对比走势的职责由 §3.3 的大图承担。

**三种卡态**：

| 卡态   | 判定                 | 呈现                                                                                           |
| ------ | -------------------- | ---------------------------------------------------------------------------------------------- |
| 正常   | 已结算 ≥ 阈值        | 完整 sparkline + 4 数字                                                                        |
| 小样本 | 已结算 > 0 但 < 阈值 | 同上，但元信息行加 `⚠ 已结算仅 N 仓` 警示                                                      |
| 空档   | 已结算 = 0           | **虚线边框**，不画曲线，一句说明（有持仓→「等待首次结算」；无持仓→「阈值较高，等待信号命中」） |

空档态是这次改版里最重要的一块：它把「还没轮到它」和「它跑了但没赚到钱」在视觉上区分开。小样本警示同理 —— 一个 ROI +6.5% 若只有 3 仓，与另一档 +8.2% 但 21 仓的可信度差着数量级，数字旁边不放线索，读者无从判断。

### 3.2 详情层（信息去哪了）

现有两个独立弹窗（`AccountPlanDialog`「账户推演」、`HistoryDialog`「操作历史」）加上下沉的 10 个指标，合并成**一个策略详情弹窗**，内部分四区：

| 区           | 内容                                                                     |
| ------------ | ------------------------------------------------------------------------ |
| 战绩全景     | 完整 14 指标（含平均年化、开始/运行时间、峰值占用）                      |
| 成本四段分解 | 追价成本 → 延迟成本 → 执行滑点 → 协议费 → 净盈亏（含成本，带覆盖率标注） |
| 账户推演     | 现有 `AccountPlanDialog` 内容原样搬入                                    |
| 操作历史     | 现有 `HistoryDialog` 内容原样搬入                                        |

**成本四段分解为什么值得单独成区**：它现在散落在卡片的四个并列 Metric 里，读者看不出它们是**一条链** ——

1. **追价成本**：我们比聪明钱买贵了多少
2. **延迟成本**：信号形成到我们跟进之间，价格漂了多少
3. **执行滑点**：吃盘口的真实成本（CLOB 盘口快照模拟吃单）
4. **协议费**：taker 费，实测约名义额 2.5%

四项串起来才回答「纸面盈亏和实盘差在哪」。拆成四个孤立数字，等于把一个推导过程摊平成四个互不相干的事实。

### 3.3 大图层（族筛选 + hover 高亮）

保留「结算净值曲线」，加三项改动：

1. **默认只画有已结算仓的档** —— 空档现在会画成一条贴零轴的平线，是纯噪音
2. **族开关**：四个族各一个 toggle，默认全开；点某族只看该族。族内最多 5 条线，永远不会拥挤
3. **hover 图例高亮**：悬停某条图例 → 该线加粗，其余降到 20% 透明度

`STRATEGY_STROKES` 已在上一批扩到 12 种「4 色 × 3 线型」的可区分组合（相邻下标线型必不同，色盲友好），本次不动。

## 4. 已知限制

- **sparkline 不可横比**：这是 U5 的代价。两张卡的曲线看起来一样陡，实际幅度可能差 10 倍。缓解手段是卡上的 4 个数字本身可横比，以及大图提供统一坐标系。
- **卡片仍不排序**（U2）：读者要自己扫视 12 张卡找最好的那个。族分组把扫视范围缩到 2–5 张，但没有消除扫视。若将来样本充足，可以再议排序（届时需要解决「小样本虚高」，见 `2026-08-11` 那份设计的 §9.2 伪独立性讨论）。
- **前端改动无自动化测试覆盖**：这个项目的测试都是 `lib/` 层纯函数，`app/` 下没有组件测试。验收靠 `npm run typecheck` + 真机目视。若要提取纯逻辑（如卡态判定、sparkline 定域），应放进 `lib/` 并配单测。

---

## 5. 不做

- 排序 / 打分 / 「推荐档位」标记 —— U2 已裁决，且小样本下任何排序都会制造误导性的第一名
- 跨档聚合 KPI —— 与「战绩不可跨档相加」的口径声明直接冲突
- 卡片密度自适应 / 用户自定义列 —— YAGNI
