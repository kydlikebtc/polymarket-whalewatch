# 战绩口径纠错四件套 — 设计文档

> 状态：2026-08-04 设计评审通过并已实施（提交 80d2d34 / bb4fe4f / c769797 / 0e52e33 / bbc2b61 / fd6c3f4）。
> 起因：整体 review 发现对外发布的战绩数字存在四处系统性偏差，且**全部偏向让数字更好看**。

## 1. 问题陈述

这个项目唯一没被同类工具复制的资产是「可信度」——每条推送都带着自己的 30 天价格调整战绩。
review 查出四处口径错误，共同特征是：**都让对外数字偏乐观**。一个没有对照的系统会朝着让作者
感觉良好的方向漂移，而这套系统恰恰把可信度当成全部价值主张。

| #   | 问题                     | 偏差方向                                   |
| --- | ------------------------ | ------------------------------------------ |
| U1  | SELL 侧 implied 基准反号 | 卖出侧的零优势策略被认证成 alpha           |
| U2  | 共识升级行重复计入战绩   | 强信号被加权，且破坏显著性判据的独立性假设 |
| U3  | 协议费完全未入账         | 遗漏的正是执行成本里最大的一项             |
| U4  | 争议中的市场照常结算     | 把可能被推翻的价格永久钉死进战绩           |

## 2. 各单元设计

### U1 · SELL 侧 implied 反号

`settleWon` 判 SELL 赢的条件是 `resolutionPrice < entry`，而 `implied` 基准逐行累加原始成交价。
方向不一致：SELL@0.20 的赢面，市场自己给的是 0.80 而不是 0.20。

**修法**：`impliedWinProb(price, side) = side === "SELL" ? 1 - price : price`，作为零假设的唯一定义，
`implied` 与 `variance` 都过它。三处 SQL 补 `COALESCE(payload.side, 'BUY')`——共识 payload 无 side
键且本身即净买入，默认值正确。

**实测量级**：10 笔 SELL@0.20 全归零（市场自己给 80% 概率的教科书级零优势结果），
旧口径 `wins=10 / implied=2.0 / 超额 +8.0 = 6.3σ` → 推送印「已超运气范围」；
修正后 `implied=8.0 / 超额 +2.0 = 1.58σ` → 落回运气范围内。SD 不受影响（`p(1−p)` 关于 0.5 对称），
错的只有零假设的中心，而那正是决定「像不像 alpha」的那一半。

### U2 · escalation 折叠

`consensus` 的 `dedup_key` 含 `walletCount`，一个组 2→3→4 人写三条 alerts 行。

**保留哪一行**：形成时刻那条（`created_at` 最早）。它是读者当时真正能按那个价格行动的一条；
升级行报的是市场已经走过去的价。

**两处现场，共享规则而非代码**：`lib/signalRecord.foldEscalations` 与
`lib/outcomeStats.foldAlertEscalations`。刻意不复用——`outcomeStats` 被打进客户端包，
不能引入 `better-sqlite3` 依赖链。

**折叠键来源**：服务端由既有 `dedup_key` 剥掉末段得到（`consensus:<cid>:<outcome>:<n>` → 去掉 `:<n>`），
不重解析 payload。单笔成交恒为 null——每笔是独立决策，折叠会丢样本。

**两个边界**：

- 折叠在价格过滤**之后**：否则「形成行无价」会把整条信号连同它可评分的升级行一起吞掉。
- 缺 `conditionId`/`outcome` 的行不折叠：误合并会静默删样本，漏合并只是多计，两害相权取后者。

### U3 · 协议费入账

**推翻的前提**：「Polymarket 零手续费」。2026-08-04 实测 gamma `/markets`，按 24h 量降序头部 100 个
开放市场：**72 个 `feesEnabled=true`，占 24h 总成交量 57.8%**，`feeType` 横跨 7 个品类
（sports/politics/crypto/weather/culture/economics/finance），不是只有体育。
已结算市场仍返回 `feeSchedule`（20 行样本全带）。

**公式与那个反直觉结论**：

```
fee = shares × rate × p × (1−p),  shares = sizeUsd / p
    = sizeUsd × rate × (1−p)
```

`p(1−p)` 在 0.5 处最大是**每股**的形状。对**固定金额**买单，份额随 p 变小而膨胀，
两个效应合并后是随 p **单调递减**：$500 @0.2 = $20（名义额 4%）、@0.5 = $12.5（2.5%）、@0.9 = $2.5（0.5%）。
**冷门票才是相对最贵的那一批**，不是 50/50 盘。已写单测钉死。

**为什么这一项最重要**：同一笔 $500 单，实测盘口滑点 $0.00 而 taker 费约 2.5%，
而 `/follow` 页此前正把前者标注为「真实执行成本的实测估计」。

**口径裁决（用户决定）**：

- `realized_pnl` 定义不变，新增 `fee_usd` 列，展示层拆三档：纸面 / 含追价成本 / 含协议费。
  理由：费率表只能拿到当前值，硬并进主账会静默重写已发布数字，且此后分不清亏损来自判断还是执行。
- **老仓不回填**，`fee_usd` 恒 null。理由：回填会造出一个看不出是估算的估算。
  与 `exec_*` 同为 append-only 归因列。

**未知 vs 零**：`feesEnabled=false` → 0（确实免费）；收费但费率表缺失、或 `exponent ≠ 1`
（实测样本恒为 1，未观测形态不猜）→ **null**。把未知当 0 正是「零手续费」这个错误前提
能活六周的机制。

**同口径纪律**：三档相减用 `slippageCostSettled`（仅已结算仓）而非看板上覆盖全部仓位的
`slippageCost`——`totalRealized` 与 `feeCost` 都是 settled 口径，混用等于把还没兑现的成本
提前记进已结算账。第三档仅在已结算仓费用**全部已知**时才给数字，否则留白。

**费用只收一次**：`follow_positions` 唯一的出场路径是 `status='settled'`（市场关闭后按
`outcomePrices` 赎回），赎回不是成交、不产生 taker 费。

### U4 · UMA 争议门

`umaResolutionStatuses` 是**字符串化 JSON 数组**（不是数组），取值只见过 `"proposed"` / `"disputed"`。

**关键形态**：`["proposed","disputed","proposed","disputed"]`——争议后会重新提案。
所以「当前是否争议中」是**最后一个元素**，不是「数组里含不含 disputed」；后者会让任何
被争议过的市场永久冻结结算。开放市场样本里约 1.5% 处于争议中。

**为什么必须拦**：两条结算路径都是一次性写入——`follow` 的 `realized_pnl` 写完不再重算，
`alertOutcomes` 的 `won` 一旦写入就直接进 30 天战绩的分子分母。

**fail-open**：严格 `=== true` 才拦，`null`（未知 / 上游没这个字段）照常结算。一个新字段
拿不到不该冻结全局结算。

**配套**：`closed` 但争议中的市场，gamma 缓存从「永不刷新」改 30min TTL，否则争议期的
临时结果会被永久缓存住。

## 3. 缓存版本迁移

`MarketMeta` 新增四个字段。`closed` 市场的缓存「永不过期」是结算回填赖以成立的前提，
代价是新字段对老行永远为空——版本号是唯一解。`META_V = 2`，写入时带上、读取时比对，
不匹配即判为 miss。一次性重取后即稳定。

## 4. 测试策略

- 纯函数优先：`lib/fees.ts`、`parseUmaDisputed`、`foldEscalations` 全部可独立断言
- U1 的验收断言是**具体数字**（`implied` 从 2.0 → 8.0），而非「行为正确」
- U4 的取值表直接来自实测样本，含那个「争议后重新提案」的反直觉形态
- 三条 fail-open 用例（`umaDisputed=null` 照常结算）与三条 fail-closed 用例配对
- 新增 ~20 个用例，全量 733 绿

## 5. 已知遗留

- U1/U2 会让已发布的历史战绩数字变化（很可能变差）。这是纠错的必然结果，
  但**尚未在页面/推送上加版本说明**——老读者可能以为在粉饰。建议随下一次
  面向读者的改动一并补一行「口径修订于 2026-08-04」。
- `docs/signals-api.md` 描述的 `record30d` 语义被 U1/U2 改变（同样的原始数据现在算出
  不同的数字），文档未更新。
- 协议费只覆盖新开的仓，样本要几周才积累起来；在此之前第三档大概率留白。
