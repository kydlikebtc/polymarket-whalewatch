# 市场深度卡对外 API —— 交易者下单前的那一眼

日期：2026-08-21
状态：**已实现**（批次 1）。实现计划见 `2026-08-21-market-card-api.md`

> **实现时与本文的一处偏离：§3.3 的 L2（`market_card_cache` 表）已砍掉。**
> 贵的是窗口不是卡片——`composeMarketBrief` 是纯函数、告警命中史是本地 SQL、
> 钱包账龄永久缓存，拿陈旧窗口重算一张卡几乎不要钱。降级路径直接是「用陈旧窗口
> 重算」，不必再存一份卡。L2 唯一还能救的场景是「进程刚重启 + 立刻遭遇突发」，
> 而重启后令牌桶恰好是空的、冷取预算充足——窗口窄到不值一张表。按 YAGNI 砍掉，
> 批次 1 少一个有状态组件。§4 的响应契约与 §5 的落点参数全部照原样实现。
>
> 另有一处实现时才补的红线：**降级路径连 gamma 元信息也不许再取**（`metaFetcher`
> 顶成只读缓存）。此前 `getMarketMeta` 写死直连，meta TTL 1 小时，于是预算耗尽时
> 重算卡片仍可能捅一次上游——一条声称零上游的路径上藏着网络调用，契约就是假的。

## 1. 现状与问题

🎯 市场信号卡这个模块**已经存在且分层干净**，缺的不是能力，是对外的形态：

| 层     | 文件                            | 职责                                                             |
| ------ | ------------------------------- | ---------------------------------------------------------------- |
| 纯计算 | `lib/marketBrief.ts`            | 分类（共识/分歧/无）+ 聪明钱按结果的留存敞口 + 拆单建仓组        |
| 组装   | `lib/marketCard.ts`             | gamma 元信息 + 24h 成交窗口 + 新钱包异动（账龄）+ 本地告警命中史 |
| 出口   | `app/api/market/[conditionId]/` | 已是一个路由：60s promise 缓存 + IP 限流，**无 key**             |
| 消费   | 网页 `/market/[cid]`、TG bot 🎯 | 一套实现喂两个面                                                 |

**需求**：订阅方的用户**正要在某个市场下单**，想先看一眼这个市场的深度分析——
谁在买、多强、成本多少、有没有分歧、我们历史上在这里发过什么信号准不准。

这个场景对数据新鲜度是硬要求：**过时的盘面回答不了「我现在该不该进」**。

### 已否决：快照卡

曾考虑让引擎在信号成立时组装卡片落库，API 纯本地读（零上游，与 `/api/signals`
同纪律）。**用户否决**，理由成立：快照回答的是「信号成立那一刻这个市场长什么样」，
那是存证/复盘的价值；而交易决策要的是**此刻**。两件事，不能互相代替。

快照方案仍保留一个残影——L2 降级底座（§3.3），但它是地板不是地面。

### 真正的技术问题：并发

`/api/signals` 的安全性来自「零上游调用」，突发流量永远挤不占引擎的 data-api
预算。**市场卡恰好相反**：一张冷卡要打 gamma + 多页 `/trades` + 钱包账龄探测，
而且调用方**点名任意 conditionId**。

现有限流 `{ perIp: 120, global: 600, cost: 2 }` = 每 IP 60 req/min、全局
300 req/min。**它限的是请求数 N，而成本取决于去重后的市场数 M** ——
拦得住「一个人狂刷同一个市场」（那本来就被 promise cache 合并成免费），
拦不住「三百个人各看一个不同市场」（那才要命）。**闸门装错了维度。**

## 2. 成本基线

### 引擎稳态

| 循环          | 节奏       | 每轮上游请求                   | 折算         |
| ------------- | ---------- | ------------------------------ | ------------ |
| 告警循环      | 4s         | 通常 1 页（`hasSeenAny` 止页） | ~15 req/min  |
| 共识深窗      | 5min       | BUY+SELL 各 ≤20 页             | ~4–8 req/min |
| 跟单执行层    | 5min       | 每新仓 1 次 `/book`            | ~1 req/min   |
| 结算/证据回填 | 10min / 6h | 批量                           | 零星         |

**稳态约 20–25 req/min ≈ 0.4 req/s**，外加每日播种/发现的突发（已刻意串行化）。

### 一张卡

| 部分                | 请求数   | 说明                                           |
| ------------------- | -------- | ---------------------------------------------- |
| `fetchMarketWindow` | **1–13** | 24h / $500 / 250 每页 / offset 上限 3000，串行 |
| `getMarketMeta`     | 0–1      | `market_meta` 有缓存                           |
| `getWalletAges`     | 0–24     | ≤12 钱包；`first_ts` 永久缓存，未命中约 2 请求 |

典型热门市场 ≈ 5–8 个请求；最坏 ≈ 38 个。

## 3. 架构

### 3.1 增量续抓 —— 打破新鲜度与容量的零和

整窗重抓的浪费在于：24 小时里只有最近这一分钟是新的，其余 23h59m 完全没变，
**每次刷新都在重付已经付过的钱**。

引擎的告警循环早就不这么干（`hasSeenAny`：一旦某页碰到已处理的成交，更深的页
就是旧闻，翻页即止）。同一招用到卡片上：

**保留窗口，只续新的。** `/trades` 是 newest-first、250 条一页；记住上次见到的
最新成交时刻，续抓时抓第 0 页、撞到已见即停。单个市场要在 TTL 内新增超过 250 笔
$500+ 成交才需要第二页——实际不会发生。

> **冷启 1–13 个请求（只付一次），热续 1 个请求（确定性）。**

容量对比（预算固定 100 req/min）：

|                        | 整窗重抓 | 增量续抓 |
| ---------------------- | -------- | -------- |
| 每次刷新成本           | ~8 请求  | **1**    |
| 每分钟可刷新次数       | 12.5     | **100**  |
| 30s 新鲜度下的活市场数 | 6        | **50**   |
| 60s 新鲜度下的活市场数 | 12       | **100**  |

同样的上游预算，容量翻 8 倍，且在更新鲜的档位上。

### 3.2 窗口层（新增，有状态）

进程内 LRU，键 = conditionId：

```typescript
interface WindowEntry {
  trades: Trade[]; // 24h 窗口内，newest-first
  newestTs: number; // 续抓锚点：上次见到的最新成交时刻
  builtAt: number; // 本窗口最后一次成功续抓的时刻
}
```

- 每次续抓后**滚动裁剪**尾部超出 24h 的成交（窗口是滑动的，不是累积的）；
- LRU 上限按**市场数**（默认 200）淘汰；单市场 24h/$500 约几百到几千笔
  （~200KB），200 个约 40MB，进程内放得下；
- **重启丢工作集**——第一批请求退化成冷启，代价是几十次冷取，可接受。
  落 SQLite 能扛重启，但要付写入量；先做内存版，观测后再决定。

### 3.3 三层 + 令牌桶

```
请求 → L1 进程内 promise cache（30s）   ← 合并同 cid 并发，命中零上游
     → 窗口层续抓（需取 1 枚令牌）      ← 全局预算，硬上限
     → 预算耗尽 / 上游失败 → L2 降级    ← 持久化上一份卡 + staleSec
     → L2 也没有 或 超陈旧闸 → 429      ← 宁可拒绝，不给会误导的旧卡
```

**L2 表**：

```sql
CREATE TABLE IF NOT EXISTS market_card_cache (
  condition_id TEXT PRIMARY KEY,
  card_json    TEXT NOT NULL,
  built_at     INTEGER NOT NULL
);
```

只存**最近一次成功构建**的卡（不留历史）。用途有二：预算耗尽时的降级底座、
进程重启后的兜底。

**令牌桶**计量的是**冷取/续抓次数**而非请求次数——这正是 §1 说的「把闸门挪到
对的维度」。进程内实现（单 Next 进程，与 `apiGuard` 的限流表同一姿态）。

### 3.4 预算从属引擎健康度

「服务性能允许的范围」不该是拍脑袋的常数，判据仓库里现成：`heartbeats` 表记着
每个循环的 `last_ts` / `max_gap_sec`，`evaluateHealth()` 能算出 `staleLoops`
（`/api/signals` 每次请求都在调它）。

| 引擎状态                       | 卡片预算          |
| ------------------------------ | ----------------- |
| 全部循环准时                   | 满额 100 req/min  |
| 有循环漂移（gap 超预期未判死） | 线性降到 25%      |
| `staleLoops` 非空              | **归零，只发 L2** |

引擎永远优先：它断更了，卡片再新鲜也没有意义——而且断更的原因很可能就是
data-api 被挤爆，此时继续取令牌是在加深故障。

### 3.5 共享，不隔离

网页 `/market/[cid]` 与 TG bot **走同一个窗口层、同一个令牌桶**：

- 上游预算本来就是同一份，分两个桶只是把同一个天花板切成两半；
- 人在看的热门市场正好也是订阅方在看的，**共享工作集是净收益**（互相预热）。

内部路由保留现有的 `guardExpensive`（防单 IP 滥用），叠加在桶之上。

## 4. 对外端点契约

**新端点** `GET /api/signals/market/[conditionId]`，与 `/api/signals` 并列于
对外命名空间，鉴权复用 `checkFeedAccess`。

**不复用** `/api/market/[cid]`：那条路由服务网页与 bot（无 key），把「强制鉴权 +
范围 + 令牌桶 + 陈旧闸」和「本地免鉴权」两套策略塞进一个路由会很脏，而且对外契约
一旦定了就不能随网页需求自由改。两条路由共用 `buildMarketCard`——与「bot 和
dashboard 共用一份实现」是同一个模式。

**订阅范围**：新增 `market`，与既有 `strategy` / `large` / `consensus` /
`discovery` 同构（走 `busTypeAllowed` 那套），**realtime tier 专属**。

> 这不违反「延迟是唯一杠杆、字段不阉割」：那条纪律管的是同一端点内不同 tier 的
> 字段集；范围机制本来就是「没订阅就拿不到」。深度决策卡是实时能力，卖给实时订户。

**响应**：

```typescript
interface MarketCardResponse {
  card: MarketCard; // 与内部同构（identity/meta/brief/freshFlow/history/window）
  builtAt: number; // 本卡的数据基准时刻
  staleSec: number; // 响应时刻 − builtAt
  live: boolean; // true = 本次现算；false = L2 降级
  healthy: boolean; // 引擎健康位，与 /api/signals 同义
  notice: string; // 研究用途 · 非投资建议 · 只读非托管
}
```

**降级语义**：

| 情形                    | 返回                              |
| ----------------------- | --------------------------------- |
| L1 命中                 | 200，`live: true`                 |
| 续抓成功                | 200，`live: true`，`staleSec ≈ 0` |
| 预算耗尽，L2 在陈旧闸内 | 200，`live: false` + `staleSec`   |
| L2 超陈旧闸 / 无 L2     | **429** + `Retry-After`           |
| 引擎 `staleLoops` 非空  | 同上两行，且 `healthy: false`     |

## 5. 落点参数

| 参数               | 值              | 依据                                               |
| ------------------ | --------------- | -------------------------------------------------- |
| L1 TTL             | **30s**         | 卡片年龄上限                                       |
| 硬陈旧闸           | **90s**         | 超过就拒绝，不给会误导的旧卡                       |
| 令牌预算           | **100 req/min** | 引擎稳态的 4 倍；实测 `/positions` 15 req/s 才限频 |
| 窗口 LRU 上限      | **200 市场**    | ~40MB                                              |
| 稳态可服务活市场数 | **~50**         | 30s 新鲜度下；随预算线性可调                       |

全部走 `lib/config.ts` 的环境变量解析（坏值回默认并 warn，与既有姿态一致）。

## 6. 为什么陈旧闸是硬拒绝而不是「带标志照给」

卡片说「3 个聪明钱刚买了 YES」，若其中 2 个在这几分钟里已经卖了，这张卡不是
「不够新」，是**错的**，而且错在会让人亏钱的方向上。

带 `staleSec` 让客户端自己判断是不够的——客户端会为了不显示空白而照渲染。
契约层面拒绝，才是真的拒绝。

## 7. 红线

1. **引擎优先**：`staleLoops` 非空 → 预算归零。卡片系统在任何情况下都不得
   把引擎挤下线。
2. **零新增引擎负担**：卡片系统的一切都在请求侧，**不得在引擎循环里跑任何东西**
   （与 bus 投影相反——那个是引擎的活）。
3. **陈旧不得超闸**：宁可 429。
4. **上游是无版本公开 API**：`/activity` 的 limit 曾从 1000 静默降到 500，
   直接把钱包档案页全挂。把这个能力写进对外文档 = 把一个我们控制不了、会不打
   招呼变形的依赖接到 SLA 上。**必须在 api-access.md 里对订阅方讲明白**，
   `/api/signals` 没有这个暴露面。
